# Velvet v0.5.30 — Sonos Keeps Playing While the Browser Sleeps

v0.5.29's end-of-track fix helped, then a whole afternoon of a genuinely
backgrounded browser tab exposed the harder version of the same problem: a
web player that is not running at all cannot move on to the next track, no
matter how smart its end-of-track logic is. This release moves the safety net
from "the browser eventually notices" to "the room keeps playing regardless."

## The room could still go silent — if the browser tab froze, not just lagged

Chrome doesn't just slow down a hidden tab, it can fully freeze one after a
while unless it's playing audible media — and a tab casting to Sonos is silent
by design, keep-alive or not. A frozen tab runs no JavaScript at all: no
heartbeat, no Auto-DJ pick, nothing. The evidence was in the log itself: a
normal Auto-DJ pick logs two Last.fm similar-artist lookups two seconds apart;
one track that afternoon logged exactly one and then nothing, ever, for that
track. The queue simply stopped growing, and when the speaker later finished
it, the server had nothing left to advance to.

**The server now picks one plain track itself when that happens.** When the
speaker finishes a track and the saved queue has run out — meaning the
browser's own pick chain stalled — the server casts one track from the user's
own library scope, no Auto-DJ scoring (the same tier a third-party client's
shuffle gets), and logs it distinctly (`cast-queue ▶ … (server fallback
pick: …)`) so it's never mistaken for a real Auto-DJ decision. The browser's
own Auto-DJ takes back over automatically the moment it's next alive. The
room's silence no longer depends on the browser waking up in time.

## The Now Playing bar could lag behind what was actually playing

A related symptom from the same session: Auto-DJ had correctly moved on to a
new track — visible in the log, in the similar-artist lookups, in what was
audibly playing — but the on-screen Now Playing bar stayed on the previous
song. The bar's update code was ordered *after* other per-track work (loading
the audio element, fetching the waveform, casting to Sonos) that doesn't
always finish in a heavily throttled tab, so it silently never ran. The bar,
queue highlight and BPM/key chips now update first, from the queue state
alone, before any of that — the display can no longer be held hostage by a
side effect that stalls.

## A closer attempt at keeping the tab from freezing at all

The keep-alive signal added in v0.5.29 (to stop the browser's playback clock
from lagging) used a silent, non-oscillating DC offset — which almost
certainly doesn't count as "audible" to the browser's own freeze-exemption
check, since it produces no sound at any volume. It's now a genuinely
oscillating tone at 17.4 kHz, quiet enough that essentially nobody will notice
it at normal listening levels, aimed specifically at that exemption. This is
best-effort and unverified — no web page can force a browser to never freeze a
hidden tab — which is exactly why the server-side fallback above exists as the
part that's actually guaranteed.

## Upgrade note

Restart the server after upgrading, and **hard-refresh the web player** — all
three changes live in the browser.
