# Velvet v0.6.11 — New: Admin → Network Shares, plus LXC contribution fixes

A new admin feature, plus two fixes aimed at bringing the Proxmox LXC
installer closer to what community-scripts' own contribution guidelines
actually require.

## Mount an NFS or SMB share directly from the admin UI

A new **Admin → Network Shares** page mounts an NFS or SMB/CIFS share
directly from inside Velvet, no shell access to the server needed. It
works on any install running as root, which covers most Docker and
bare-metal setups, and a privileged LXC or Incus container.

It needs Velvet's own process to be running as root, since mounting a
filesystem is a privileged kernel operation no matter which user asks for
it, and nothing about this feature tries to escalate Velvet's own
privilege to get there. On an **unprivileged** container, the default for
this project's own LXC/Incus installer, this can never work at all, a
confirmed kernel limitation covered in [`docs/lxc-incus.md`](../docs/lxc-incus.md).
The page recognizes that exact failure and explains it directly, rather
than showing a generic error.

## Why now

This came out of checking Velvet's Proxmox LXC installer directly against
[community-scripts' own contribution guidelines](https://community-scripts.org/docs/contribution/readme)
for anyone who eventually wants to submit it to their catalog. Their
review checklist is explicit: a platform-neutral container-creation script
must have no hand-written host commands. The wizard's own NFS/SMB mounting
is built from exactly that — `pct`/`incus` calls, writing the host's own
`/etc/fstab` — which wouldn't pass review as it stands.

This feature is the real fix, not a workaround: a submission-ready version
of the installer can skip all of that host-level work entirely and just
point the admin here afterward, once the container already exists. This
repo's own one-command installer keeps its existing automatic mounting
unchanged — the two are independent, and either can be used on its own.

## Also: the installer's bootstrap now matches their template

`ct/velvet.sh` now tries a local sibling `core` checkout before falling
back to `curl` to fetch the engine — the exact pattern community-scripts'
own contribution template uses, and the specific thing their review
checklist checks for. No change for the normal one-line install, which has
no local checkout and falls straight through to the same `curl` fetch as
before.

## Details

New endpoints: `GET`/`POST /api/v1/admin/network-mount` and
`DELETE /api/v1/admin/network-mount/:name`, documented in `docs/API.md`.
Full write-up of the feature, including exactly what it needs and when it
can't work, in [`docs/network-shares.md`](../docs/network-shares.md).

## Verified

24 new automated tests cover the input validation and the `/etc/fstab`
handling directly, the parts worth getting exactly right since they touch
a real system file. The full suite: 328 of 328. All 12 locale files are in
sync. The actual live mount/fstab behavior still needs a real host to
exercise end to end, the same caveat as the rest of this install path.
