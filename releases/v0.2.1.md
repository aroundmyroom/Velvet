# Velvet v0.2.1 — Subsonic play-queue restore fix

A focused fix release for Subsonic clients (Feishin, and any client that uses
server-side play-queue persistence).

## Fixed

### Restored play queues now advance correctly

Reopening a Subsonic client with a partially-played queue that had been saved on
the server could leave playback stuck:

- at the end of the resumed track, playback paused instead of advancing;
- pressing **Next** moved the highlight forward but didn't start playing;
- the queue could play the *previous* track while the UI showed the next one.

**Cause.** `getPlayQueue` returned the stored `current` track id exactly as the
client had saved it, but rebuilt every queue entry's id in Velvet's canonical
`<hash>@<rowid>` form. Two situations made the two diverge:

- **After upgrading Velvet** — queues saved by an older version stored bare
  content-hash ids, while entries now come back as `<hash>@<rowid>`.
- **After a library rescan** — the embedded SQLite rowid is reassigned when a file
  is re-indexed, so a saved `…@<oldrowid>` no longer matched.

When `current` matched none of the returned entries, the client could not locate
its resume point and mis-advanced.

**Fix.**

- `getPlayQueue` now re-encodes `current` through the same resolver used for the
  entries, so it is always byte-identical to one of the returned entry ids; if the
  current track is no longer in the library it falls back to the head of the queue.
- `savePlayQueue` canonicalises the queue and current ids before storing them, so
  newly-saved queues stay consistent even across rescans.

Two integration tests cover the bare-hash-restore and unresolvable-current cases.

## Upgrade notes

No action required. Existing saved queues — including bare-hash queues from older
versions — are healed automatically on the next `getPlayQueue`.
