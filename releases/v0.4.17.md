# v0.4.17 — Boot Hold

## What's new

### Boot hold: survive disk-full and storage I/O errors

When Velvet cannot open its SQLite database due to a known environmental problem, it no longer crashes and leaves the port dead. It binds the configured port immediately and serves a self-refreshing 503 diagnosis page.

**Covered failure categories:**

| Category | Typical cause |
|---|---|
| `disk-full` | Volume with the database is at or near 0 bytes free |
| `db-io` | WAL shared-memory error — common on FUSE, sshfs, mergerfs without WAL-safe config |
| `db-damaged` | Database file is corrupt or truncated |
| `db-unwritable` | PUID/PGID mismatch — process can't write to the DB directory |
| `db-locked` | Another process holds a lock, or filesystem (CIFS/NFS) breaks byte-range locking |
| `db-missing-dir` | Configured database directory doesn't exist or isn't accessible |

Velvet retries a full boot every **15 seconds**. When the problem is resolved (space freed, volume remounted, permissions fixed) it recovers automatically.

**API response during hold** — clients that send `Accept: application/json` or `x-access-token` receive:
```json
{ "error": "boot-hold", "category": "disk-full", "message": "Disk full" }
```
with `X-Velvet-Boot-Hold: disk-full` and `Retry-After: 15` headers and HTTP 503.

**Tuning:** set `VELVET_BOOT_HOLD_RETRY_MS=5000` in the environment to change the retry interval (default 15 000 ms).

Unclassified failures (migration bugs, code errors) still crash immediately so they remain loud and visible in logs.
