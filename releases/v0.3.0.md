# Velvet v0.3.0 — Library: orphaned vpath detection and cleanup

## Problem

When a library folder is renamed or removed from config, the scanner only
cleans up rows within the vpath it just scanned. Rows for the old name remain
in the database indefinitely. This caused the Album-Art Workshop to throw
**"vpath X is not a root folder"** when it tried to resolve the disk path for
those stale rows.

The only previous fix was manual SQL + a full rescan.

## What's new

### Automatic guard in the Album-Art Workshop

`_reconcileCandidates()` now skips any row whose vpath is not a current root
folder in config. Stale entries never enter the `album_art_workshop` table,
and any existing ones are silently cleaned up on the next suggest pass. The
"vpath X is not a root folder" error no longer occurs.

### Post-scan warning in the log

After every scan, Velvet checks whether any vpaths remain in `files` that are
no longer in config. If found, a `[finish-scan]` warning is logged pointing
the admin to the new cleanup tool.

### Admin — Purge orphaned vpaths (Admin → Library)

A new card in the Library / DB admin view lets you safely clean up orphaned
rows without touching the database manually:

1. Click **Purge orphaned vpaths** — a dry-run fires first and shows the
   affected vpath names and row count.
2. Confirm — rows are deleted from both `files` and `album_art_workshop`.

### New API endpoint

`POST /api/v1/admin/db/purge-orphaned-vpaths`

| Field | Type | Description |
|---|---|---|
| `dryRun` | boolean | If `true`, returns counts without deleting |

Response: `{ orphaned: string[], deleted: number }`
