# v0.4.9

Fix two regressions from v0.4.7–v0.4.8 that broke transcoding and made the Symfonium library appear empty.

## Fixed: `getTranscodeDecision` could return `canDirectPlay:false` AND `canTranscode:false` simultaneously

v0.4.7 added a check that blocked direct play when `maxAudioBitrate` was exceeded (e.g. a FLAC at 800 kbps with `maxAudioBitrate:192000`). This is correct when transcoding is available as an alternative. However, when Velvet's transcoding is disabled, the result was `canDirectPlay:false AND canTranscode:false`. Symfonium interprets this as the file being completely unplayable — so the entire library appeared empty.

**Fix:** the bitrate cap now only blocks direct play when transcoding is actually enabled. When transcoding is disabled, `canDirectPlay` is based solely on the container format check — the client direct-plays regardless of bitrate, since that is the only available option.

## Fixed: `setup()` calling full `init()` unconditionally could interfere with existing FFmpeg binary

v0.4.8 changed server startup to call the full `init()` path (which runs `ensureFfmpeg()`, potentially triggering a download or upgrade check) regardless of whether transcoding was enabled. This could interact unexpectedly with an already-working FFmpeg installation — particularly in Docker where the binary is pre-bundled.

**Fix:** restored the v0.4.7 behaviour — full `init()` only runs when `transcode.enabled:true`. When disabled, a lightweight file-existence probe is used instead, which is sufficient to set the binary as "Ready" in the admin panel without touching the binary.
