# Velvet v0.7.0 — Security release: full static-analysis audit of the whole codebase

Velvet's entire codebase went through a full security scan for this release,
and every real issue it turned up is fixed. Updating is recommended for
everyone, especially if your Velvet is reachable from the internet or shared
with other people.

Nothing changes in how Velvet looks or works.

## How the audit was done

- **Scanner:** [opengrep](https://github.com/opengrep/opengrep) 1.32.0, with
  572 rules for JavaScript, TypeScript, leaked secrets, the Dockerfile, the CI
  workflows, shell scripts and HTML.
- **Scope:** every file in the repository, including the two large web
  frontends (over 1 MB each) that the scanner skips by default.
- **Triage:** all 2,072 findings were reviewed. Most are pattern matches that
  can't tell escaped from unescaped output. For those, every place where data
  is inserted into HTML or XML was traced back to where the data comes from.
- **Result:** 34 new automated tests guard the fixes. The full suite (362
  tests) passes, and none of the rules reports a new problem.

## What was fixed

### Server-side request forgery (SSRF)

Velvet refuses to fetch radio streams, logos and podcasts from addresses
inside your own network, so a URL can't be used to reach your router or other
local services. That check only looked at how the address was *written*. It
could be bypassed with:

- a domain name that points to an internal address;
- `0.0.0.0`;
- an IPv6 address in brackets, such as `[::1]`;
- a public URL that redirects to an internal one.

Velvet now resolves the name, checks every address it resolves to, connects
only to the address it checked, and repeats that for every redirect.

### Jukebox / remote control

The jukebox stored session codes in a way that treated special names such as
`__proto__` as valid codes. Without logging in, someone could use that to fake
the "now playing" information of other remote-control sessions. Sessions are
now stored safely.

### Cross-site scripting (XSS)

In a few places, text that comes from your files or from outside services was
put into a page without escaping. A file, folder, tag or online service with a
crafted name could then run script in your browser. Fixed in:

- **Player:**
  - folder names in the file explorer and Tag Workshop breadcrumbs;
  - Sonos favourites and browse results;
  - cover suggestions from Deezer, iTunes and Discogs;
  - album years and track numbers;
  - the library name in the scan-progress card.
- **Admin:**
  - confirm dialogs that showed usernames, folder names or album paths;
  - pop-up messages that showed error text from the server.
- **Mobile player:** radio station logos.

As an extra layer, cover art and radio logos are now served with a strict
sandbox policy. Even a malicious SVG logo can't run script when someone opens
it directly.

### Sonos, DLNA and Subsonic

- **Sonos:** one browse request accepted a parameter that ended up unchecked
  in the command sent to your speaker. It now accepts only its two valid values.
- **DLNA:** year, track number and file size are always sent as plain numbers.
- **Subsonic:** a tag containing an invalid control character could break a
  Subsonic app's parser. Those characters are now removed from the response.

### Smaller fixes

- **Migration import:** uploading an import ZIP could crash the whole server.
  The import part of migration was never finished, so it now replies "Import
  is not available yet" instead. Export is unaffected.
- **Migration routes:** two related routes could be pointed at any folder in
  the server's temp directory. They now only accept their own import IDs.
- **Tag Workshop:** a manually entered year is now always saved as a number.
