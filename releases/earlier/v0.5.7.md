# Velvet v0.5.7 — Correct HTTP Status Codes

This hardening release replaces a set of generic 500 "Server Error" responses
with correct, specific HTTP status codes, and makes the recursive file listing
resilient to unreadable folders. The improvements were identified by reviewing
recent upstream mStream activity and implemented natively for Velvet.

## Library access answers 404, not 500

Requesting an unknown library, or a library the user has not been granted,
now answers **404 Not Found**. Previously these requests surfaced as a 500
"Server Error", which polluted the server logs with false alarms and gave
clients no way to distinguish a real fault from a bad path.

This applies everywhere a vpath is resolved — file explorer, downloads,
metadata lookups, scrobbling by filepath, and every other endpoint that
takes a `Library/path` style argument.

## Admin user management answers 409 and 404

- Adding a username that already exists → **409 Conflict**
- Deleting, changing the password or Subsonic password, editing vpaths or
  admin access, linking Last.fm, or toggling any permission (radio recording,
  YouTube download, upload, server remote, MPV cast) for a user that does not
  exist → **404 Not Found**

The admin UI keeps working unchanged; scripts and API consumers now get
actionable status codes instead of 500.

## Admin file explorer rejects malformed paths

A directory path containing a NUL byte is rejected with **400 Bad Request**
before any filesystem access happens.

## Recursive listing survives unreadable subfolders

`POST /api/v1/file-explorer/recursive` (used by "add folder to queue") now
skips a subfolder it cannot read — a permission error on one directory no
longer aborts the entire listing with a 500. The skipped folder is logged
as a warning on the server.

## Upgrade note

Restart the server after upgrading. No configuration or database changes.
