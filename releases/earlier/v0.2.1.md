# Velvet v0.2.1 — Subsonic server-side play-queue consistency

A focused fix for **server-side play-queue persistence** — the Subsonic
`savePlayQueue` / `getPlayQueue` endpoints used by clients such as DSub and
play:Sub to store and restore a listening queue on the server.

## Fixed

### `getPlayQueue` `current` now always matches a returned entry

When a client restored a queue from the server, the `current` (resume) track id
could fail to match any of the queue entries:

- `getPlayQueue` returned the stored `current` id **verbatim**, but rebuilt every
  entry id in Velvet's canonical `<hash>@<rowid>` form.
- The two diverged after **upgrading Velvet** (older queues stored bare
  content-hash ids) or after a **library rescan** (the SQLite rowid embedded in
  each id is reassigned when a file is re-indexed).

When `current` matched none of the entries, a client could lose its resume point.

**Fix.**

- `getPlayQueue` re-encodes `current` through the same resolver used for the
  entries, so it is always byte-identical to one of the returned entry ids; if the
  current track is no longer in the library it falls back to the head of the queue.
- `savePlayQueue` canonicalises the queue and current ids before storing them, so
  newly-saved queues stay consistent even across rescans.

Two integration tests cover the bare-hash-restore and unresolvable-current cases.

## Scope

This change only affects clients that use **server-side** queue persistence. It
does **not** change behaviour for clients that keep their queue entirely on the
client (e.g. Feishin, which never calls `savePlayQueue` / `getPlayQueue`).

A separately reported Feishin issue — a restored or replaced queue playing the
**previous queue's next track** — was investigated against the access logs and
traced to Feishin's own gapless prefetch (the wrong track is chosen client-side,
before any request reaches Velvet). It is therefore **not** fixed by this release
and is not a server-side bug. Findings and a workaround are in
`docs/dev/feishin-gapless-findings.md`.

## Upgrade notes

No action required. Existing server-side queues — including bare-hash queues from
older versions — are healed automatically on the next `getPlayQueue`.
